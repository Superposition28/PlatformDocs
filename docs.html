PlatformDocs Documentation Guide

CONVENTIONS & ARCHITECTURE

PlatformDocs is a standalone, pure-static clean-room reference for platform-inherited binary formats across 11 hardware and OS targets. Every specification is structured so an independent engineer can implement a conforming parser or loader without external code or proprietary SDKs.

1. Strict Scope Boundary

Every file documented in PlatformDocs must be inherited directly from the target platform, console SDK, boot ROM, or operating system. A format belongs here only if the platform vendor's hardware, firmware, system shell, or standard OS loader requires or defines it.

  • In scope: Cartridge/ROM headers, optical disc image filesystems and volume descriptors, platform executables and relocatable modules, system metadata descriptors (such as title IDs, parental ratings, and region flags), system banners/icons/trophies, digital distribution packages, and standard OS debug/installer containers.
  • Out of scope: All title-specific assets, third-party middleware packs, studio scene/mesh/texture containers, audio banks, level scripts, localization tables, and proprietary studio archive formats. Never include title names, studio names, or game-specific file paths in specifications.

Boundary check: If a file extension or container is created by a third-party engine or individual software title rather than mandated by the platform holder or OS ABI, it does not belong in PlatformDocs.

2. Executable & Binary Rule

Platform executables, firmware images, and dynamic/relocatable libraries (such as GBA/NDS ROM images, GameCube/Wii .dol and .rel, PSP .prx, PS2 .elf/.irx, PS3/PS4 SELF/FSELF, Windows PE/COFF, Xbox .xbe, and Xbox 360 .xex) are documented strictly at the container, loader, and ABI boundary:

  • Document in full: Container wrappers, magic signatures, architecture/machine identifiers, program and section headers, segment/section tables, BSS declarations, import/export tables, relocation record types, entry points, and OS/SDK capability or entitlement metadata.
  • Generalized loader mapping only: Describe how a loader validates bounds, decompresses or unwraps segments, maps code/data payloads into virtual or physical memory, zero-fills BSS ranges, and applies relocations. Do not document instruction-set emulation, title-specific symbol maps, or proprietary runtime logic.

3. Clean-Room 6-Section Specification Standard

Every format page under platforms/<slug>/ must present a consistent header block (<h1>, .format-summary with <dl> metadata, and .page-toc) followed by six numbered sections with stable anchor IDs:

Mandatory 6-Section Format Page Structure
Section Anchor ID Required Contents
1. Identification & Scope #identification Canonical filenames/extensions, exact magic bytes (hex and ASCII), endianness, platform/OS applicability, and system role.
2. Binary Layout Tables #layout Scrollable .format-counts tables (Offset | Size | Type | Field | Description) for every header, directory, and sub-record using exact hex offsets and fixed-width types (u8, u16le/u16be, u32le/u32be, u64le/u64be, char[N]).
3. Flags, Enums & Decoding Formulas #flags Bitmasks, enumeration tables, address/offset derivation formulas, pixel/tile/compression math, and version-to-version deltas.
4. Edge Cases & Loader/Parser Rules #edge-cases Bounds and overflow checks, alignment/padding rules, zero-size or sentinel records, revision branching, and generalized loader mapping.
5. Step-by-Step Pseudocode #pseudocode Complete, clean-room parser pseudocode inside <pre><code> covering validation, header parsing, table traversal, and error exits.
6. Provenance & Confidence #provenance Explicit separation of confirmed hardware/OS specs, SDK-revision-dependent behavior, and unverified/reserved fields using .callout-warn for caveats.

4. Provenance & Confidence Conventions

Specifications must never conflate verified ABI definitions with empirical guesses or fabricate undocumented constants. Classify structural claims explicitly using the shared badge conventions:

Confirmed Spec SDK-Revision-Dependent Unverified / Reserved Platform-Inherited
  • Confirmed Spec: Verified against public hardware documentation, open ABI specifications, boot ROM invariants, or deterministic format checks across retail media.
  • SDK-Revision-Dependent: Header sizes, optional extended headers, encryption/signing wrappers, or enum values known to vary across SDK generations, hardware revisions, or system firmware updates.
  • Unverified / Reserved: Fields observed as zero-filled padding, opaque capability bits, or vendor-reserved bytes whose exact runtime interpretation is not independently confirmed.

No fabricated constants: If a cryptographic key, hash seed, or undocumented bitflag cannot be stated from verified public knowledge, record it explicitly as reserved or vendor-private rather than inventing a placeholder value.

5. Static file:// Shell & Lazy Iframe Routing Architecture

The documentation site runs directly from the local filesystem via file:// without a local web server, build step, or JavaScript framework:

  • CSS :target routing: index.html renders #home by default when no fragment is active (.home-page { display: block; }) and hides it whenever any .page:target matches (.pages:has(.page:target) .home-page:not(:target)).
  • Lazy-loaded iframes: Each guide, platform overview, and format specification is declared as <iframe class="page" id="<route>" data-src="<path>" src="about:blank" loading="lazy">. All 54 content pages stay unloaded at about:blank until selected.
  • Minimal hash router script: On initial load and hashchange, the inline script in index.html reads location.hash, assigns iframe.src = iframe.dataset.src on first visit if still blank, and updates the fixed topbar's #up-link target (format routes <platform>-<format> resolve up to #<platform>; platform overviews and #docs-guide resolve up to #home).
  • Standalone compatibility: Every page under platforms/ and docs.html links style/main.css relatively and sets target="_top" on breadcrumb links so pages work both inside the shell iframe and when opened directly.

6. Adding a New Platform or Format Page

  1. Verify scope: Confirm the format is strictly platform-inherited (boot, container, executable, OS metadata, or system UI) with zero title-specific dependencies.
  2. Create the HTML page: Add platforms/<slug>/index.html (for a new platform) or platforms/<slug>/<format>.html using <body class="doc-page">, ../../style/main.css, and target="_top" breadcrumbs pointing to ../../index.html#home and ../../index.html#<slug>.
  3. Follow the 6-section contract: Populate .format-summary, .page-toc, and all six sections (#identification, #layout, #flags, #edge-cases, #pseudocode, #provenance).
  4. Register the route in index.html:
    • Add the lazy <iframe class="page" id="<route>" data-src="platforms/<slug>/<file>.html" src="about:blank" loading="lazy" title="..."></iframe> inside <main class="pages">.
    • Add the link to the platform's card in .documentation-tree and update the summary counts in .format-coverage.
    • If adding a new platform slug, add it to the longest-first prefix list in the inline #up-link script in index.html (for example, ensuring longer prefixes such as xbox360 precede shorter prefixes such as xbox).
  5. Validate via file://: Open index.html directly in a browser, verify #home, #docs-guide, the platform overview, the format page, Up / Back navigation, and narrow viewport wrapping (<= 600px).
