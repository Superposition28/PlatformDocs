XDBF — Xbox Database Format (.gpd / .spa)

Indexed Resource Database · Xbox 360 Profiles & Title Metadata

Lightweight, namespace-indexed binary database format used both for Xbox 360 title service definitions embedded inside XEX2 executables (.spa) and for per-title/account profile state stored inside CON STFS packages (.gpd).

1. Identification & Scope

XDBF (Xbox Database Format) provides an indexed, append/free-list-managed blob store keyed by a (Namespace, ID) pair. On Xbox 360 it serves two closely linked roles:

  • .spa (System / Title Service Package): Embedded inside a title's XEX2 Resource Info table (under the 8-hex-character Title ID resource name). Stores static title definitions: achievement definitions, localized strings, icons, contexts, properties, and stats schemas.
  • .gpd (Game Profile Data): Stored inside the user's CON STFS profile package. Each played title has a <TitleID>.gpd recording unlocked achievements, timestamps, settings, and Xbox LIVE sync cursors; the special dashboard file FFFE07D1.gpd tracks played titles, profile gamerpic/motto settings, and total gamerscore.

Endianness Detection Flag / Convention: Standard Xbox 360 XDBF files are Big-Endian, beginning with ASCII "XDBF" (58 44 42 46) and Version = 0x00010000 (00 01 00 00). Little-Endian XDBF files (used by Windows SDK/authoring tools) store those same 32-bit header integers in Little-Endian, appearing on disk as "FBDX" (46 42 44 58) and 00 00 01 00. Parsers must check the byte order of Magic and Version before decoding any table.

3. Flags, Enums & Decoding Formulas

Data Offset Calculation

The byte tables are pre-allocated with fixed capacity; active entries occupy only the leading slots, while the Data Region begins strictly after the allocated capacity of both tables:

EntryTableOffset     = 0x18
FreeSpaceTableOffset = 0x18 + (EntryTableLength * 18)
DataStart            = 0x18 + (EntryTableLength * 18) + (FreeSpaceTableLength * 8)
EntryFileOffset(i)   = DataStart + Entry[i].OffsetSpecifier

GPD Xbox LIVE Sync Records

Within any synchronized .gpd namespace (typically Namespaces 1, 3, 4, and 6), two reserved 64-bit IDs manage delta synchronization with Xbox LIVE:

  • Sync List (ID = 0x0000000100000000): Array of 16-byte records { u64be EntryID, u64be SyncID } mapping each local entry to its monotonic sync revision.
  • Sync Data (ID = 0x0000000200000000): 24-byte header { u64be NextSyncID, u64be LastSyncID, u64be LastSyncTime } tracking the high-water mark of the last successful server sync.

4. Edge Cases & Loader Rules

  • Capacity vs. Active Count: Never compute DataStart using EntryCount or FreeSpaceTableCount. Unused slots between EntryCount and EntryTableLength (and between FreeSpaceTableCount and FreeSpaceTableLength) are reserved space; DataStart always uses EntryTableLength and FreeSpaceTableLength.
  • Relative Offsets: OffsetSpecifier in both the Entry Table and Free Space Table is relative to DataStart, not file offset 0x00.
  • Reserved Sync IDs in Namespace Enumeration: When enumerating achievements, settings, or titles in a .gpd, skip entries with ID == 0x0000000100000000 or 0x0000000200000000 (or ID == 0), as these are sync control blocks rather than user records.
  • Free-Space Hole Coalescing: Modifying or deleting entries in-place records freed byte ranges in the Free Space Table rather than compacting the Data Region immediately. Parsers reading unmodified entries ignore the Free Space Table, while writers must allocate from best-fit holes or append to DataEnd.
  • .spa vs. .gpd Payload Format: Inside .spa files, Namespace 1 and Namespace 5 blobs are structured chunks beginning with 4-byte ASCII tags (e.g., XTHD, XACH, XSTR) and version/size headers, whereas .gpd files store raw binary achievement/setting/title records directly.

5. Step-by-Step Parser Pseudocode

function ParseXdbf(stream):
    magicBytes = stream.ReadBytes(0x00, 4)
    if magicBytes == "XDBF":
        endian = "BE"
    elif magicBytes == "FBDX":
        endian = "LE"
    else:
        raise InvalidXdbfMagic

    ReadU16 = (endian == "BE") ? stream.ReadU16BE : stream.ReadU16LE
    ReadU32 = (endian == "BE") ? stream.ReadU32BE : stream.ReadU32LE
    ReadU64 = (endian == "BE") ? stream.ReadU64BE : stream.ReadU64LE

    version = ReadU32(0x04)
    assert version == 0x00010000

    entryTableLen = ReadU32(0x08)
    entryCount    = ReadU32(0x0C)
    freeTableLen  = ReadU32(0x10)
    freeCount     = ReadU32(0x14)

    assert entryCount <= entryTableLen and freeCount <= freeTableLen

    entryOffset = 0x18
    freeOffset  = 0x18 + entryTableLen * 18
    dataStart   = freeOffset + freeTableLen * 8

    entries = []
    for i in 0 .. entryCount - 1:
        pos = entryOffset + i * 18
        ns     = ReadU16(pos + 0x00)
        id     = ReadU64(pos + 0x02)
        relOff = ReadU32(pos + 0x0A)
        length = ReadU32(pos + 0x0E)
        payload = stream.ReadBytes(dataStart + relOff, length)
        entries.append({ Namespace: ns, ID: id, Offset: dataStart + relOff, Length: length, Data: payload })

    freeSpaces = []
    for i in 0 .. freeCount - 1:
        pos = freeOffset + i * 8
        freeSpaces.append({ Offset: dataStart + ReadU32(pos), Length: ReadU32(pos + 4) })

    return { Endianness: endian, Entries: entries, FreeSpaces: freeSpaces }

6. Provenance & Confidence

Profile & Achievement Integrity Caveat: .gpd files do not carry an internal cryptographic signature of their own; their integrity and offline/online unlock trust are enforced by the enclosing CON STFS signature and Xbox LIVE server synchronization. Do not expect standalone .gpd edits to pass console verification without valid STFS container re-signing.

  • High Confidence (Confirmed Layout): The 24-byte header, 18-byte Entry Table, 8-byte Free Space Table, relative OffsetSpecifier addressing, and Namespaces 1..6 are consistently observed across .spa resources inside XEX2 binaries and .gpd files in retail profiles.
  • Sync & Extended Setting Variants: Specific Setting.ID constants and newer avatar award fields in Namespace 6 vary across dashboard kernel generations.
