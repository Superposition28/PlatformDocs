1. Hardware & OS Architecture

The Xbox 360 (codename Xenon) combines a 3-core, 6-hardware-thread 3.2 GHz PowerPC 64-bit processor with 512 MB of unified GDDR3 memory and a unified-shader GPU (Xenos). While the processor executes 64-bit PowerPC instructions and supports 64-bit integer/VMX-128 operations, the Xbox 360 runtime ABI operates in 32-bit pointer mode: virtual addresses, PE32 image bases (typically 0x82000000 for title executables), and kernel import thunks are 32-bit values.

  • Hypervisor (hv): Runs at highest privilege in real-mode memory. Enforces encrypted/hashed physical page descriptors from XEX2 images, manages RSA/AES key vaults, and exposes hardware security services through the sc syscall interface.
  • Kernel (xboxkrnl.exe): NT-derived microkernel managing threads, virtual memory (4 KB, 64 KB, and 16 MB pages), optical/HDD block devices, XDVDFS/FATX filesystems, and ordinal-based system imports.
  • Xbox Application Manager (xam.xex): System module providing dashboard services, user profiles, achievements, Xbox LIVE licensing, STFS package mounting, and XDBF profile/title database synchronization.

3. Boot, Disc & Package Ecosystem

Retail and development software reaches the console kernel through two primary distribution containers, both converging on XEX2 execution and XDBF metadata:

  • Optical Disc Path: XGD2 / XGD3 Optical Disc → Drive validates PFI/DMI/SS security sectors → Kernel mounts XDVDFS game partition (+0x10000) → Loads root default.xex (XEX2).
  • Digital / HDD / MU Path: STFS Container (CON , PIRS, LIVE) on FATX storage → Kernel/Xam verifies RSA signature & L0/L1/L2 SHA-1 hash tree → Exposes inner default.xex, DLC archives, or profile .gpd files.
  • Metadata & Profile Path: XEX2 resource section embeds a .spa (XDBF) package describing achievements, localized strings, and icons; xam.xex projects those definitions into the user profile's per-title .gpd inside a CON STFS package.

4. Hybrid Endianness Notes

Unlike pure big-endian or pure little-endian consoles, Xbox 360 platform formats consistently mix byte orders because Microsoft adapted x86/PC specifications (PE/COFF, XDVDFS, FAT timestamps) onto a big-endian PowerPC host:

  • XEX2: Big-endian container headers, optional header directory, security info, and PPC32 machine code—wrapping Little-Endian DOS/NT/PE32/Section headers.
  • STFS: Predominantly Big-Endian metadata and hash next-pointers (u24be), combined with Little-Endian volume descriptor block counts/indices (u16le, u24le) and Little-Endian u24le block fields inside file entries.
  • XDBF: Native console .spa and .gpd files use Big-Endian XDBF headers and payloads, while PC SDK/tooling variants use Little-Endian byte order indicated by the magic/version byte order.
  • XGD / XDVDFS: Little-Endian XDVDFS volume descriptors and binary-search-tree directory nodes paired with Big-Endian DVD-ROM physical/security descriptors.
