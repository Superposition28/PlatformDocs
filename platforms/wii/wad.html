Wii .wad Title / Channel Package Format

Signed Title Archive · Route #wii-wad

Nintendo Wii's 64-byte-aligned package container encapsulating a Certificate Chain, optional CRL, Ticket, Title Metadata (TMD), AES-128-CBC encrypted content blobs (.app), and an optional footer for NAND title installation.

Canonical Filenames
*.wad (e.g., system/IOS packages inside disc update partitions under _sys/, or standalone channel installers)
Magic Bytes
No fixed ASCII magic; identified by 0x00000020 header size at 0x00 and 2-byte type tag (Is = 0x4973, Ib/ib = 0x4962/0x6962, Bk = 0x426B) at 0x04
Endianness
Big-endian throughout header, Ticket, TMD, certificates, and metadata
Platform/OS Scope
Nintendo Wii (RVL) IOS ES (/dev/es) installer, disc update partition, and System Menu backup format
Role/MIME
Encrypted, signed Wii NAND title installation package (application/x-wii-wad)

1. Identification & Scope

A Wii .wad file (unrelated to id Software's Doom WAD format) bundles all authentication records and encrypted content files required to install a 64-bit Title ID onto Wii NAND flash. Every section is stored sequentially and padded with zero bytes to a strict 64-byte (0x40) boundary.

  • Header Signature: Bytes 0x00–0x03 contain big-endian 0x00000020 (32-byte header size), followed at 0x04–0x05 by the 2-byte ASCII WAD type ("Is" = 49 73, "Ib"/"ib" = 49 62 / 69 62, or "Bk" = 42 6B) and 0x0000 at 0x06–0x07.
  • Endianness: All header lengths, Ticket fields, TMD fields, and certificate structures are big-endian.

2. Binary Layout Tables

Table 2.1 — WAD File Header (0x00–0x1F, Padded to 0x40)
Offset Size Type Field Description
0x00 4 u32be HeaderSize Always 0x00000020 (32 bytes; padded to 0x40 in file).
0x04 2 char[2] WadType Package type tag: "Is" (installable), "Ib"/"ib" (boot/internal), or "Bk" (backup).
0x06 2 u16be Padding Reserved/version field (typically 0x0000).
0x08 4 u32be CertChainSize Unpadded byte size of the Certificate Chain section.
0x0C 4 u32be CrlSize Unpadded byte size of the Certificate Revocation List (typically 0).
0x10 4 u32be TicketSize Unpadded byte size of the Ticket (0x2A4 for standard v0 Ticket).
0x14 4 u32be TmdSize Unpadded byte size of the TMD (0x1E4 + 0x24 * NumContents).
0x18 4 u32be DataSize Total byte size of the encrypted content data section (sum of 64-byte-aligned content blobs).
0x1C 4 u32be FooterSize Unpadded byte size of the optional trailing footer (typically 0 in Is WADs).
0x20 32 u8[32] HeaderPad Zero-byte padding to 64-byte alignment (0x40).
Table 2.2 — Sequential 64-Byte-Aligned WAD Sections
Offset Size Type Field Description
0x40 align64(CertChainSize) Cert[] CertChain Concatenated CA, XS, and CP certificates verifying Ticket and TMD signatures.
offcrl align64(CrlSize) u8[] CrlSection Optional Certificate Revocation List (0 bytes if CrlSize == 0).
offtik align64(TicketSize) Ticket TicketSection v0 Ticket (0x2A4 bytes + 0x1C pad = 0x2C0) with encrypted Title Key.
offtmd align64(TmdSize) TMD TmdSection Title Metadata declaring NumContents, BootIndex, and 36-byte Content Records.
offdata align64(DataSize) Blob[] ContentBlobs NumContents sequential AES-128-CBC encrypted content blobs, each padded to 64 bytes.
offftr align64(FooterSize) u8[] FooterSection Optional metadata/banner footer (0 bytes if FooterSize == 0).
Table 2.3 — Backup (Bk) Variant Header Note (0x426B, e.g. SD Export)
Offset Size Type Field Description
0x00 4 u32be HeaderSize Header size (0x00000070 in SD content.bin backup header; 0x00000020 in standalone Bk WADs).
0x04 2 char[2] WadType "Bk" (0x426B) identifying backup/console-bound package semantics.
0x08..0x1F 24 u32be[6] SectionSizes In Bk WADs, footer/backup metadata or console ID fields may accompany the standard size table.

3. Flags, Enums & Decoding Formulas

3.1 64-Byte Alignment Formula

Every section offset is derived cumulatively using 64-byte alignment:

align64(n) = (n + 0x3F) & ~0x3F   // equivalently: ((n + 63) // 64) * 64
  • off_cert = align64(HeaderSize) (0x40 for standard 0x20 header)
  • off_crl = off_cert + align64(CertChainSize)
  • off_tik = off_crl + align64(CrlSize)
  • off_tmd = off_tik + align64(TicketSize)
  • off_data = off_tmd + align64(TmdSize)
  • off_ftr = off_data + align64(DataSize)

3.2 AES-128-CBC Title Key & Content Blob Decryption

  1. Decrypt Title Key from Ticket:
    • Select Common Key using Ticket[0x1F1] (0x00 = Wii Common Key; 0x01 = Korean Common Key).
    • IV = Ticket[0x1DC..0x1E3] || 0x00[8] (8-byte Title ID + 8 zero bytes).
    • TitleKey = AES_128_CBC_Decrypt(CommonKey, IV_title, Ticket[0x1BF..0x1CE]).
  2. Decrypt Each Content Blob i (0 .. TMD.NumContents - 1):
    • Encrypted length in WAD = align16(Content[i].ContentSize), followed by zero padding up to align64(Content[i].ContentSize) (total span in WAD = align64(Content[i].ContentSize)).
    • IV for content i = Content[i].ContentIndex (u16be, 2 bytes) || 0x00[14] (big-endian 16-bit content index followed by 14 zero bytes).
    • PlainPadded = AES_128_CBC_Decrypt(TitleKey, IV_content, Blob[0 : align16(ContentSize)]).
    • Truncate PlainPadded to exact Content[i].ContentSize bytes and verify SHA1(Plain) == Content[i].ContentSha1.

3.3 Content Type Flags & NAND Filenames

  • 0x0001: Normal private content installed under /title/<type>/<id>/content/<CID_hex8>.app.
  • 0x4001: DLC content.
  • 0x8001: Shared content (referenced by SHA-1 in /shared1/content.map on NAND).

4. Edge Cases & Loader/Parser Rules

  • WAD Type Variants (Is, Ib/ib, Bk):
    • Is (0x4973): Standard installable title/channel/IOS WAD used in disc update partitions and system packages.
    • Ib / ib (0x4962 / 0x6962): Internal/boot WAD variant used for boot2 or internal Nintendo provisioning packages; follows the same 0x20 header and 64-byte-aligned layout.
    • Bk (0x426B): Backup WAD / SD-exported channel container; may carry non-zero FooterSize (console/backup metadata) or use the 0x70-byte SD backup header when stored as content.bin on SD. Parsers must check HeaderSize at 0x00 and WadType at 0x04 rather than hardcoding Is.
  • Padding vs. Encrypted Block Size: AES-128-CBC requires a 16-byte multiple, whereas WAD sections align to 64 bytes. When ContentSize is not a multiple of 16, only align16(ContentSize) bytes are AES-encrypted (or all align64 bytes are encrypted depending on packer), so always decrypt align64(ContentSize) or align16(ContentSize) and slice to ContentSize before SHA-1 verification (since CBC decryption of earlier blocks does not depend on trailing blocks).
  • Non-Zero Footer: Some packages append a non-zero Footer (e.g., 0x40-aligned metadata or display/backup descriptor). Check FooterSize > 0 and validate against total file size.
  • Boot Content Mapping: In installed NAND titles, Content[TMD.BootIndex] is the executable payload: either a static .dol binary or a minimal NAND loader stub chained to the main .dol content, mapped into MEM1/MEM2 after Starlet loads TMD.SystemVersion.

5. Step-by-Step Parser Pseudocode

function parse_wad(stream, common_keys):
    hdr = read_bytes(stream, 0x00, 0x20)
    hdr_size  = u32be(hdr, 0x00)
    wad_type  = ascii(hdr, 0x04, 2)
    cert_size = u32be(hdr, 0x08)
    crl_size  = u32be(hdr, 0x0C)
    tik_size  = u32be(hdr, 0x10)
    tmd_size  = u32be(hdr, 0x14)
    data_size = u32be(hdr, 0x18)
    ftr_size  = u32be(hdr, 0x1C)

    assert hdr_size == 0x20
    assert wad_type in ["Is", "Ib", "ib", "Bk"]

    off_cert = align64(hdr_size)
    off_crl  = off_cert + align64(cert_size)
    off_tik  = off_crl  + align64(crl_size)
    off_tmd  = off_tik  + align64(tik_size)
    off_data = off_tmd  + align64(tmd_size)
    off_ftr  = off_data + align64(data_size)

    certs  = read_bytes(stream, off_cert, cert_size)
    crl    = read_bytes(stream, off_crl,  crl_size)
    ticket = read_bytes(stream, off_tik,  tik_size)
    tmd    = read_bytes(stream, off_tmd,  tmd_size)
    footer = read_bytes(stream, off_ftr,  ftr_size)

    key_idx = ticket[0x1F1]
    iv_title = ticket[0x1DC : 0x1E4] + bytes(8 zero bytes)
    title_key = aes128_cbc_decrypt(common_keys[key_idx], iv_title, ticket[0x1BF : 0x1CF])

    num_contents = u16be(tmd, 0x1DE)
    boot_index   = u16be(tmd, 0x1E0)
    cursor = off_data
    contents = []

    for i in 0..(num_contents - 1):
        rec = tmd[0x1E4 + i * 0x24 : 0x1E4 + (i + 1) * 0x24]
        cid        = u32be(rec, 0x00)
        cindex     = u16be(rec, 0x04)
        ctype      = u16be(rec, 0x06)
        csize      = u64be(rec, 0x08)
        expected_h = rec[0x10 : 0x24]

        enc_span = align64(csize)
        enc_blob = read_bytes(stream, cursor, enc_span)
        cursor += enc_span

        iv_c = u16be_bytes(cindex) + bytes(14 zero bytes)
        dec_padded = aes128_cbc_decrypt(title_key, iv_c, enc_blob[0 : align16(csize)])
        payload = dec_padded[0 : csize]
        assert sha1(payload) == expected_h

        contents.append({
            id: cid, index: cindex, type: ctype,
            is_boot: (i == boot_index), data: payload
        })

    return { wad_type, certs, crl, ticket, tmd, contents, footer }

6. Provenance & Confidence

Cryptographic & Key Caveat: Retail Wii Common Keys, Korean Common Keys, and Nintendo CA/XS/CP private signing keys are omitted. Decryption requires external user-supplied keys; additionally, personalized or SD Bk packages may encrypt content or Ticket keys with console-unique NG/PRNG keys rather than the global Common Key.
  • Confirmed Specification: The 0x20-byte WAD header, 64-byte alignment rule, Ticket/TMD layouts, Title Key IV (TitleID || 0x00*8), and per-content IV (ContentIndex || 0x00*14) are confirmed across IOS /dev/es installation packages and official disc update WADs.
  • Variant-Dependent Fields: Header bytes 0x06–0x07 and the exact payload format inside non-zero Bk footers vary across Nintendo internal/backup tooling revisions.
